### Linux Node 22 committed input follow-up

An actual Docker build on Linux Node 22.23.4 exposed a real input race after the visible registration-ready frame. A disposable diagnostic copy of the compiled callback and original test reproduced it: at the `n` key, the callback saw `busy:false`, `registered:true`, but still had `registration:true` in its previous closure. Ink installs `useInput` callbacks in passive React effects; the visible frame could therefore disagree with input routing until those effects ran. This was not a persisted registration failure or a reason to remove the model admission guard.

`CoordinationPanel` now installs a stable forwarding callback and publishes its latest committed handler ref in `useLayoutEffect`. Handler changes never mutate refs during render. The latest active/busy guards remain, as does functional view-key accumulation. A separate no-`act` regression schedules `n` as a microtask from the committed ready frame, before passive input-listener replacement: the original production code fails on actual Linux Node22 (`.cache/tui-registration-layout-before.log`), while the fixed code opens the new-request draft without sending it. The settled registration form test separately uses React `act`, current-frame checks and actual last-frame diagnostics; it is not used to erase the interleaving from the regression.

`.cache/tui-registration-layout-linux-node22.log` records the full compiled suite on actual Linux Node22.23.4; `.cache/tui-registration-layout-all.log` records the host suite. Both require all 47 tests to pass with zero skips, including rapid view keys, agreement next/previous, inactive input and the new committed-frame race. The Linux run uses a disposable container with current emitted modules/tests and the existing source image's locked runtime dependencies. It does not replace the parent's final full Docker build gate or packaged-artifact rebuild after this production fix.
