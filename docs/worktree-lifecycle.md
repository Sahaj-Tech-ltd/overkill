# Managed worktree lifecycle

The `internal/worktree.Manager` allocates a separate Git checkout and branch per task. It is a checkout lifecycle primitive; allocation by itself does not assign coordination tasks, select the runtime workspace, merge changes, or prove that tests passed.

Each allocation uses a readable task prefix followed by the full SHA-256 of the original task ID. Path-shaped IDs such as `a/b` and `a-b` therefore remain distinct, including after restart. The default branch is `overkill/parallel/<allocation-name>`. Empty, dot, dot-dot, control-character, and oversized task IDs are rejected. A custom allocation root must be one immediate directory name under the canonical repository checkout root. Repository symlink aliases are canonicalized; symlink allocation roots and checkout paths are rejected.

A kernel file lock in Git's shared administrative directory serializes allocation, cleanup and recovery across managers and processes. The lock is released by the operating system when a process exits. It serializes lifecycle mutations; it does not grant exclusive agent execution or prevent humans and other Git clients from changing the repository.

Ownership records live beside the checkouts under the managed root. Each record preserves the original task ID, branch, path, creation time, Git administrative directory and a random allocation token. The token is also written to that administrative directory. Recovery only accepts matching records, immediate checkout paths, Git worktree registrations, branches and tokens. It does not infer ownership from a path prefix. Legacy checkouts without records, arbitrary nested worktrees and replacement checkouts are left alone. `Reclaim` refreshes the manager's in-memory inventory; `Get` and `List` return copies of that inventory, rather than live filesystem guarantees. Acquire and release revalidate durable ownership under the lifecycle lock.

`Add` uses an existing branch at its current commit or creates a new branch from HEAD. It never implicitly resets an existing branch with `-B`. Git still rejects branches checked out elsewhere. Acquisition returns the verified existing allocation on retry and rejects a conflicting branch override. It preserves an unowned directory at the target path. Errors persisting ownership or locking retain the checkout for inspection rather than recursively deleting it.

Managed release verifies ownership again before removal. It refuses modified, untracked and ignored files, including when the legacy `Force` option is set. `ForceFresh` also requires a clean verified allocation and keeps its branch history. This prevents automatic failure cleanup from destroying unfinished work. A Git lock with a reason different from the recorded manager lock is preserved. Requested branch deletion uses `git branch -d`, preserving unmerged commits; an error explains when the checkout was removed but the branch remains. Repeated release after a successful removal is a no-op. Low-level `RemoveForce` remains an explicitly destructive API for callers that independently authorize discarding work; the manager does not use it.

The checks are designed for cooperating application processes and ordinary concurrent Git use. They do not sandbox a hostile process running as the same operating-system user, or make filesystem validation atomic against arbitrary external path replacement. Git subprocesses currently use the inherited local Git configuration and hooks. Automatic stale-lock takeover, automatic legacy-worktree adoption and automatic discard are deliberately absent.

Real Git fixtures cover paths containing spaces, path-shaped task aliases, malicious IDs and roots, symlink roots and targets, existing branch history, modified/untracked/ignored file preservation, external locks, copied metadata, multiple managers and subprocesses, restart recovery, replacement administrative identities, safe double release and unmerged commit preservation. Windows locking is cross-compiled; native Windows execution remains a separate verification requirement.
