# Loaded autonomous plans

`/build /absolute/path/Plan.md` explicitly loads a Markdown plan and executes it in that same Run or Stream request. Paths preserve case and may contain spaces. With no argument, `/build` retains existing plan discovery. Missing/unreadable plans return the command's diagnostic without execution. Each `##` heading defines one sequential phase. Plan inputs must be regular files of at most 2 MiB; oversized content is rejected rather than truncated. Execution accepts 1–100 phases.

A caller may also use `SetAutoMode("auto")`, load a fresh `Plan` into the controller, and submit a normal request. `/auto` by itself keeps its existing single-task iterative behavior. Other autonomy modes and default configuration do not start loaded-plan execution.

The runtime schedules one phase at a time, placing its complete description in the conversation and telling the model to execute only that phase. After a provider answer and the post-write verification gate, the wired self-evaluation policy assesses that phase. Acceptance advances to the next phase. The final response contains the last phase's answer, with structured `plan` metadata recording every phase outcome. Acceptance is the configured confidence policy's decision, not independent proof that requirements or tests passed. With self-evaluation explicitly disabled, ordinary provider completion plus the existing verification gate is the completion policy.

All phases and revisions share one admission, one goal turn, the caller's cancellation context, and the existing total `MaxSteps` provider-step limit. Run also retains its normal task timeout. Each phase retains the self-evaluation loop's configured iteration bound. No recursive Run calls or extra goal turns are created. Provider calls use the existing request, accounting, tools, verification and observer paths. Streaming emits the first phase's token deltas, then status updates for subsequent phases/revisions and one final authoritative result; subsequent calls use Complete and do not emit token deltas.

Low-confidence exhaustion defers the current phase. Provider errors, verification failures, cancellation and emergency stop fail the in-flight phase and stop progression. Shared-step exhaustion defers the next phase without calling the provider. Later phases remain pending. Only acceptance of every phase yields `completed`; failed/deferred plans never produce a whole-plan success notification. A failed, deferred or interrupted plan requires an explicit reload to retry; later ordinary messages do not silently resume it.

`RunResult.plan`, the `plan_execution` event and `self.eval.status`'s `plan_execution` field expose bounded phase snapshots. Existing runtime-status persistence saves these snapshots per session, including failures and deferrals. Restored running plans/phases become `unconfirmed`; persistence is observational and never automatically resumes execution. The `current` flag distinguishes the most recent admitted turn's plan from history: a later ordinary turn clears it, so historical plan outcomes cannot override that turn's evaluation status. Snapshots omit phase descriptions and transcripts. The separate checklist plan store has only checked/unchecked items and is not overwritten or presented as an execution checkpoint.

## Application views and acceptance

Desktop Checks and the terminal evaluation panel show phase outcomes separately from verifier test results. Historical executions are labeled previous; a later ordinary turn clears `current` without deleting the prior execution. Unstarted phases remain explicit after failure or deferral. The native source scenario runs `/build` against a filename containing spaces, executes two real controlled-provider phases, displays the second final answer, and checks persisted phase outcomes.

Focused Run/Stream and PostgreSQL acceptance covers original admission/goal usage, per-phase completion policy, cancellation/provider errors/step limits, one terminal callback with truthful acceptance, cold `unconfirmed` recovery and later-turn status isolation. A separate input test rejects non-regular and oversized plan inputs before parsing. Full source acceptance is recorded in the root delivery/audit checkpoints. These fixtures do not establish autonomous paid-provider task quality or resumable checkpoints.
