# CLI and TUI credential persistence

CLI `setup` and TUI `config.create` onboarding now use the same `Config.SaveWithCredentials` path. Newly entered values in named secret fields are stored in the operating system credential vault; TOML contains an opaque `keyring://<profile-hash>/<random-id>` reference. The native adapter uses go-keyring v0.2.8 with macOS Keychain, Windows Credential Manager, and Linux Secret Service. Constructing the adapter does not access a vault. The older API AES/.master.key helper is not the new credential store.

`Config.ResolveSecrets` resolves both environment templates and keyring references before runtime use. It preserves the original reference template separately from resolved memory. Ordinary saves, including theme changes, serialize copies with those references restored. Provider reordering does not silently convert a previously resolved key back into plaintext. `MaskSecrets` also uses a deep copy and cannot overwrite live provider headers. Environment-only configuration performs no vault reads/writes; CLI setup retains a detected provider environment reference, and a default `DATABASE_URL` retains `${DATABASE_URL}` during bootstrap.

The named-field inventory covers provider keys/headers, TTS, image generation, vision, red-team/Ouroboros credentials, ACP tokens, gateway secrets, S3/share credentials, database URLs and MCP environment entries. Provider base URLs support environment references without placing every benign endpoint in a vault. Arbitrary freeform prompts, executable arguments and credentials embedded in an otherwise ordinary URL are not inferred to be secret fields. Avoid embedding secrets there.

Secure save stages new random vault entries before publishing TOML atomically. It never replaces an existing account during rotation. A vault read/write failure or failed configuration publication leaves the caller's pre-operation configuration and previous file unchanged; cleanup deletes only the newly staged accounts. Old entries remain available to backups and concurrently loaded profiles. Explicit secure Save As makes separate entries for the new profile. There is no plaintext fallback when a vault is locked or unavailable: use environment templates for headless environments or make the native vault available.

A process crash before publication, or a backend that refuses cleanup, can leave unreachable vault entries. Automatic deletion of old entries is deliberately absent because it would invalidate older configuration snapshots. The path-derived account prefix identifies the creating profile; it is not an authorization boundary against other processes running as the same user.

Existing plaintext configurations still load for compatibility, and the generic low-level `Config.Save` does not silently migrate pre-existing raw credentials. Running secure onboarding or explicitly calling `SaveWithCredentials` migrates named raw secret fields. Runtime-resolved references are protected through generic saves. Credentials still exist in process memory for API use; this change does not make them immune to a compromised user account or process.

## Acceptance evidence

`.cache/credentials-acceptance.jsonl` records 27 named race-enabled Go tests/subtests, all passing with zero skips/failures. Coverage includes real TOML load/save/restart, all inventoried fields, environment-only operation without vault calls, independent profiles, secure Save As, immutable rotation, provider reordering, atomic resolution failure, and deterministic Set/Get/publication failures. A controlled store simulates a write that succeeds before returning an error and verifies cleanup without deleting old entries.

The API tests make actual JSON-RPC HTTP requests for onboarding and theme persistence, restart by loading the saved selected profile, and resolve the references through an injected test vault. They verify that no plaintext key reaches TOML, a different default profile is not created, and vault denial preserves both disk and live configuration while suppressing backend error details. The explicit `ServerConfig.ConfigCredentialStore` constructor injection is exercised too.

`.cache/credential-config-full.log` records the full config-package race suite. Native OS vault access, CLI wizard interaction with a real vault, and cross-platform account-service availability remain separate acceptance requirements. Tests use only injected in-memory vaults and did not access or approve the host Keychain. Broader app/build validation is tracked by the main integration lane.
